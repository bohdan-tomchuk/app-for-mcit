# Специфікація: Панель обробки заявок

> Тестове завдання Full Stack Developer. Стек: Laravel + Vue 3 / TypeScript + PostgreSQL.
> Документ зведено з рішень, узгоджених під час проєктування. Статус: готово до реалізації.

## Problem Statement

Співробітникам потрібне одне місце, де можна залишити заявку (зламався принтер, потрібен доступ до VPN тощо) і бачити, що з нею відбувається. Зараз заявки губляться: автор не знає, чи хтось узяв її в роботу, а той, хто обробляє, не має єдиного списку й не бачить, хто і коли змінював статус.

З боку перевіряючого завдання проблема інша: потрібен застосунок, у якому правила доступу й переходів статусів гарантуються сервером (а не лише прихованими кнопками), зміни статусу атомарні й відстежувані, а все це покрито автоматичними тестами й запускається однією командою.

## Solution

Невеликий вебзастосунок із входом за email і паролем та двома ролями:

- **Користувач** створює заявки, бачить лише власні й може редагувати назву, опис і пріоритет, поки заявка має статус «Нова».
- **Адміністратор** бачить усі заявки й переводить їх по статусах: «Нова» → «У роботі» → «Завершена». Кожна зміна потрапляє в історію з виконавцем і часом.

Список заявок має пошук за частиною назви (без урахування регістру, зокрема для кирилиці), фільтр за статусом і серверну пагінацію. Будь-яка заборонена дія, включно з прямим HTTP-запитом в обхід інтерфейсу, відхиляється сервером без зміни даних. Реєстрації немає: акаунти створює seeder.

## User Stories

### Вхід і навігація

1. As a користувач, I want to увійти за email і паролем, so that я бачу лише свої дані.
2. As a адміністратор, I want to увійти за тим самим екраном входу, so that не потрібен окремий адмін-інтерфейс.
3. As a будь-який автентифікований юзер, I want to після входу одразу потрапляти на список заявок, so that не проходжу через порожню проміжну сторінку.
4. As a гість, I want to бути перенаправленим на вхід при спробі відкрити будь-яку сторінку заявок, so that дані недоступні без автентифікації.
5. As a гість, I want to не бачити посилання на реєстрацію, so that не намагаюся створити акаунт, який система не підтримує.
6. As a власник системи, I want to щоб роль неможливо було отримати через будь-яку форму, so that ніхто не стане адміністратором самостійно.
7. As a будь-який автентифікований юзер, I want to бачити пункт «Заявки» в бічному меню, so that завжди можу повернутися до списку.

### Створення заявки

8. As a користувач, I want to створити заявку з назвою, описом і пріоритетом, so that повідомити про проблему.
9. As a користувач, I want to щоб пріоритет за замовчуванням був «Звичайний», so that не обирати його щоразу.
10. As a користувач, I want to бачити зрозумілі українські повідомлення під полями, якщо назва чи опис порожні або задовгі, so that знаю, що виправити.
11. As a користувач, I want to щоб назва з самих пробілів вважалась порожньою, so that не створювати заявки без змісту.
12. As a користувач, I want to щоб нова заявка автоматично мала статус «Нова» і мене як автора, so that не заповнювати службові поля.
13. As a власник системи, I want to щоб сервер ігнорував підкинуті в запит статус і автора, so that ніхто не створить заявку від чужого імені чи одразу «Завершену».
14. As a користувач, I want to після створення бачити повідомлення «Заявку створено», so that знаю, що дія вдалась.
15. As a адміністратор, I want to не бачити кнопки створення заявки, so that інтерфейс відповідає моїй ролі.
16. As a власник системи, I want to щоб прямий запит адміністратора на створення заявки відхилявся, so that розподіл ролей забезпечує сервер.

## Implementation Decisions

### Каркас і оточення

- Офіційний Laravel Vue starter kit (Inertia, Vue 3, TypeScript, Tailwind, shadcn-vue, Fortify, Wayfinder). Окремий JSON API і SPA не робимо: Inertia-маршрути з Policy повністю закривають вимогу серверної перевірки.
- В інсталяторі kit'у знімаються фічі **Registration** і **Email verification**. Інсталятор сам прибирає відповідну конфігурацію, Vue-імпорти маршрутів, сторінки, тести й інтерфейс верифікації email на моделі юзера. Ручне вимкнення не годиться: згенеровані Wayfinder-імпорти маршруту реєстрації зламали б збірку фронту. 2FA, passkeys і password confirmation лишаються за замовчуванням.
- Після інсталятора вручну: middleware `verified` прибирається з маршрутів (без верифікації він нічого не робить); домашня сторінка Fortify стає списком заявок; сторінка Dashboard, її маршрут і тест видаляються; у бічному меню з'являється «Заявки».
- Оточення: Laravel Sail з PostgreSQL (без Mailpit, бо листів немає). Версія Postgres зафіксована явним тегом. Тести працюють на окремій базі `testing`, яку створює Sail, а не на SQLite: пошук через `ILIKE`, trigram-індекс і блокування рядків специфічні для Postgres.
- Мова: сторінки заявок українською. Серверні повідомлення (валідація, помилка входу, скидання пароля) українською через `laravel-lang/common` (dev-залежність, генерує файли перекладів), локаль застосунку `uk`. Сторінки auth і settings starter kit'у лишаються англійськими: у Vue kit'і немає шару i18n, а український переклад laravel-lang для нього покриває близько 11% рядків.

### Ролі

- Роль зберігається колонкою `role` у таблиці юзерів (рядок, за замовчуванням `user`) і PHP backed enum з двома значеннями: `user`, `admin`. На моделі юзера є хелпер «чи адміністратор».
- Роль виключена з масового присвоєння. Адміністратор з'являється лише через seeder.
- `spatie/laravel-permission` не використовується: ролі фіксовані, а основні правила залежать від конкретної заявки (власник, статус), тож їх усе одно реалізує Policy.

### Схема даних

**Заявки:** id; автор (FK на юзерів, індекс); назва (до 255 символів); опис (text); пріоритет (рядок `low` / `normal` / `high`, за замовчуванням `normal`, CHECK-обмеження); статус (рядок `new` / `in_progress` / `done`, за замовчуванням `new`, CHECK-обмеження, індекс); дати створення й оновлення.

**Trigram-індекс:** розширення `pg_trgm` і GIN-індекс на назві для пошуку `ILIKE '%...%'` (btree для пошуку з wildcard на початку непридатний). На малих обсягах планувальник обирає повний перегляд таблиці, і це очікувано.

**Історія змін статусу:** id; заявка (FK, заборона видалення, індекс); попередній статус і новий статус (обидва NOT NULL, CHECK-обмеження); виконавець (FK на юзерів, заборона видалення); лише дата створення (без дати оновлення, бо запис незмінний).

- Значення enum'ів зберігаються англійськими рядками; українські підписи віддає enum.
- Нативний Postgres `ENUM` і числові коди відкинуто: перший важко змінювати міграціями, другі погіршують читабельність.
- В історію пишуться **лише переходи**. Створення заявки не є зміною статусу; автор і дата створення вже є в самій заявці.

### Статусна модель

Enum статусу є єдиним джерелом правди про дозволені переходи й підписи:

| Із | Дозволено в | Підпис |
|---|---|---|
| `new` | `in_progress` | Нова |
| `in_progress` | `done` | У роботі |
| `done` | — | Завершена |

Будь-який інший перехід, включно з переходом у той самий статус, заборонений. Бібліотеки state machine не використовуються.

### Авторизація

Policy заявки:

| Дія | Дозволено | Відмова |
|---|---|---|
| список | усім автентифікованим | — |
| перегляд | адміністратору або автору | «не знайдено» (404) |
| створення | лише користувачу (не адміністратору) | «заборонено» (403) |
| редагування | автору, лише в статусі «Нова» | 404 для чужої, 403 для своєї не в статусі «Нова» |
| зміна статусу | лише адміністратору | 404 для чужої, 403 для власної заявки користувача |

- 404 для чужих заявок приховує сам факт існування запису (ID послідовні, тож 403 дозволив би з'ясувати зайняті ID перебором). 403 там, де юзер заявку бачить, але дія заборонена.
- Обмеження видимості реалізоване одним query scope «видимі для юзера» (адміністратор бачить усі, користувач лише свої). Список, пошук і фільтр завжди будуються від нього.
- Адміністратор не створює й не редагує заявки. Це **припущення**: у ТЗ створення описане як дія користувача, а редагування тексту адміністратором не вимагається.

### Маршрути (HTTP-контракт)

Усі під middleware автентифікації. Resource-маршрути заявок без видалення плюс окремий маршрут статусу:

| Метод | Шлях | Призначення |
|---|---|---|
| GET | `/tickets` | список; query: `search`, `status`, `page` |
| GET | `/tickets/create` | форма створення |
| POST | `/tickets` | створення |
| GET | `/tickets/{ticket}` | перегляд та історія |
| GET | `/tickets/{ticket}/edit` | форма редагування |
| PUT | `/tickets/{ticket}` | оновлення назви, опису, пріоритету |
| PATCH | `/tickets/{ticket}/status` | тіло: цільовий статус |

- Маршрут статусу приймає **явний цільовий статус**, а не «перевести на наступний». Так заборонений перехід можна сформулювати й перевірити, а подвійний клік чи дві вкладки дають відмову замість стрибка одразу в «Завершена».
- Статус змінюється лише окремим маршрутом. Запити створення й оновлення не знають про статус і автора; підкинуті поля відкидаються валідацією.
- Успіх: redirect назад із flash-повідомленням. Заборонений перехід: помилка валідації по полю `status` (422), дані без змін.

### Зміна статусу і конкурентність

- Окремий action «змінити статус заявки» з параметрами: заявка, цільовий статус, виконавець. Контролер лише авторизує, валідує вхід і викликає action.
- Усередині action одна транзакція: заявка перечитується з блокуванням рядка (`SELECT ... FOR UPDATE`); перевіряється дозволеність переходу; оновлюється статус; створюється запис історії з попереднім і новим статусом та виконавцем. Будь-яка помилка відкочує обидві зміни.
- Блокування гарантує, що два одночасні запити на одну заявку виконуються по черзі: другий бачить уже новий статус і отримує відмову.
- Оновлення заявки користувачем використовує той самий патерн: транзакція → перечитування з блокуванням → перевірка Policy на заблокованому рядку → оновлення. Оскільки обидві операції блокують той самий рядок, редагування й зміна статусу не перетинаються. Якщо заявку вже взяли в роботу, користувач отримує повідомлення й повертається на сторінку перегляду.

### Валідація

- Створення й оновлення: назва обов'язкова, рядок, до 255 символів; опис обов'язковий, рядок, до 5000 символів; пріоритет необов'язковий, одне зі значень enum'у (за відсутності БД і модель ставлять «Звичайний»).
- Зміна статусу: статус обов'язковий, одне зі значень enum'у статусу.
- Фільтр списку: статус необов'язковий, одне зі значень enum'у.
- Рядки з самих пробілів стають порожніми стандартними middleware обрізання й перетворення порожніх рядків на `null`.
- Повідомлення українською з laravel-lang; людські назви полів у секції атрибутів українського файлу валідації. Власні тексти повідомлень у request-класах не потрібні.

### Список

- Пошук: регістронезалежний `ILIKE` з підрядком; у введенні екрануються `\`, `%`, `_`.
- Порядок: за id від нових до старих (стабільний, на відміну від дати створення, яка в seed-даних може збігатися).
- Пагінація: 15 на сторінку, параметри пошуку й фільтра переносяться в посилання пагінації.
- Регістронезалежність `ILIKE` для кирилиці залежить від `LC_CTYPE` бази: у C-локалі вона не працює. Docker-образ Postgres за замовчуванням має UTF-8 локаль; окремий тест ловить регресію.

### Фронтенд

- Дані в Inertia props передаються лише через API Resources з явним білим списком полів (props потрапляють у HTML сторінки, тож модель цілком не віддається). Заявка: id, назва, опис, пріоритет `{value, label}`, статус `{value, label}`, автор `{id, name}`, дати, права. Запис історії: попередній і новий статус `{value, label}`, виконавець `{id, name}`, дата.
- Права обчислює сервер тією самою Policy й передає разом із даними: `can.create` (на рівні списку), `can.update`, `can.changeStatus` і `allowedTransitions` з enum'у. Vue лише рендерить, правил не дублює. Захист усе одно на сервері.
- TS-типи (заявка, запис історії, пагінований список) описані вручну; генератори типів із PHP зайві для трьох типів.
- Сторінки:
  - **Список:** поле пошуку (debounce ~300 мс, `preserveState` + `replace`), select статусу («Усі» та три статуси), «Скинути»; таблиця з колонками ID, назва (посилання), пріоритет, статус (badge), автор (лише адміністратору), створено; пагінація; два різні порожні стани; кнопка «Нова заявка» за правом створення.
  - **Створення / редагування:** один спільний компонент форми, помилки під полями, кнопка неактивна під час відправки.
  - **Перегляд:** поля, автор, дати; «Редагувати» за правом; для адміністратора кнопка на кожен дозволений перехід; помилка переходу показується на цій же сторінці; історія, що починається рядком «Створено».
- Flash-повідомлення передаються спільними props і показуються в layout. Модалок підтвердження немає: переходи односпрямовані, але не руйнівні.

### Тестові дані

- Три акаунти з паролем `password`: адміністратор `admin@example.com`, користувачі `user1@example.com` і `user2@example.com`.
- 40 заявок, по 20 на користувача: при 15 на сторінку кожен користувач бачить 2 сторінки, адміністратор 3.
- Назви з фіксованого списку реалістичних українських формулювань; слово «принтер» у різному регістрі трапляється в обох користувачів.
- Приблизно 50% «Нова», 30% «У роботі», 20% «Завершена»; у кожного користувача є всі три.
- Для кожної заявки не в статусі «Нова» є узгоджені записи історії від адміністратора з датами в минулому після дати створення. Історія пишеться seeder'ом напряму (action ставить поточний час). Дати розкидані за останні 30 днів.
- Factory заявки має стани «у роботі» й «завершена» для тестів.

### Git

- Conventional Commits, лише `type(scope): subject`, без тіла й без рядків `Co-Authored-By`. Англійською, з малої літери, наказовий спосіб, без крапки, до 50 символів.
- Scopes: `scaffold`, `sail`, `config`, `lang`, `auth`, `tickets`, `status`, `ui`, `seed`, `readme`.
- Перший коміт — чистий starter kit одразу після інсталятора, щоб diff від нього показував лише роботу над проєктом.
- Фаза 1, прямо в `main`: scaffold; Sail з Postgres; тести на Postgres; українські переклади бекенду; заміна Dashboard на список заявок.
- Фаза 2: коротка гілка на кожну фічу від свіжого `main`, тести в тій самій гілці, злиття `--no-ff`, гілка видаляється. Порядок: `feat/tickets-domain` → `feat/tickets-crud` → `feat/status-changes` → `feat/tickets-list` → `feat/tickets-ui` → `chore/seed` → `docs/readme`.

## Testing Decisions

- **Що таке хороший тест тут:** перевіряє зовнішню поведінку через HTTP так, як її бачить клієнт: статус відповіді, видимі дані та стан бази після запиту. Не перевіряє внутрішні виклики, приватні методи чи структуру класів, тому рефакторинг action'а чи Policy не ламає тести.
- **Seam один, найвищий:** feature-тести на рівні HTTP-маршрутів (запити від імені конкретного юзера → відповідь + стан БД). Окремих unit-тестів на enum чи Policy немає: матриця переходів перевіряється data provider'ом через той самий HTTP-маршрут статусу.
- **Інструменти:** PHPUnit (дефолт starter kit'у), справжній Postgres (тестова база `testing`), скидання бази між тестами. Вкладена транзакція action'а всередині тестової транзакції обробляється savepoint'ами, тож перевірка відкату коректна.
- **Prior art:** feature-тести starter kit'у для автентифікації й налаштувань профілю: той самий стиль запитів від автентифікованого юзера й перевірок відповіді.
- **Сценарії:**

| # | Сценарій | Очікування |
|---|---|---|
| 1 | Користувач переглядає, редагує й змінює статус чужої заявки прямими запитами | 404 на кожен запит, дані в БД без змін; чужих заявок немає в його списку |
| 2 | Адміністратор виконує заборонені переходи (data provider: `new→done`, `in_progress→new`, `done→in_progress`, `done→new`, `new→new`) | помилка валідації, статус і кількість записів історії без змін |
| 3 | Адміністратор проводить заявку `new → in_progress → done` | статус оновлено; в історії два записи з правильними попереднім і новим статусом та виконавцем |
| 4 | Користувач змінює статус власної заявки | 403, статус без змін |
| 5 | Користувач редагує власну заявку в статусі «У роботі» | 403, текст без змін |
| 6 | Користувач створює заявку з підкинутими статусом «Завершена» й чужим автором, без пріоритету | статус «Нова», автор — поточний юзер, пріоритет «Звичайний» |
| 7 | Пошук «ПРИНТЕР» із фільтром статусу від імені користувача | знайдено лише власні заявки зі словом «принтер» у потрібному статусі |
| 8 | Створення запису історії примусово падає під час зміни статусу | статус заявки відкотився, записів історії немає |

- Тести 1–3 закривають обов'язкові сценарії ТЗ; 4–8 закривають решту серверних правил, кириличний пошук і атомарність.

## Out of Scope

- Видалення заявок (ТЗ не вимагає).
- Реєстрація та верифікація email: акаунти створює seeder.
- Створення й редагування заявок адміністратором.
- Повна локалізація сторінок auth і settings starter kit'у (потребує `laravel-vue-i18n`, обгортання рядків у компонентах kit'у та перекладу ~164 рядків, яких немає в laravel-lang).
- Окремий JSON API / SPA.
- Динамічні ролі й дозволи (`spatie/laravel-permission`).
- Автотест реальної гонки двох адміністраторів: потребує двох паралельних з'єднань з БД і в PHPUnit крихкий; від гонки захищає блокування рядка.
- Візуальний дизайн понад компоненти starter kit'у.
- Публічне розгортання, сповіщення, коментарі до заявок, фільтри за автором і пріоритетом, сортування колонок.

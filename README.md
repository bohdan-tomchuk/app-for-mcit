# Панель обробки заявок

Вебзастосунок для подачі та обробки заявок (Laravel + Vue 3 / TypeScript + PostgreSQL). Користувач створює заявки й бачить лише власні; адміністратор бачить усі та переводить їх по статусах «Нова» → «У роботі» → «Завершена» з історією змін. Повна специфікація: [docs/SPEC.md](docs/SPEC.md).

## Швидкий запуск (лише Docker)

Потрібні тільки Docker з Compose v2; PHP, Composer і Node на хості не потрібні.

```bash
docker compose -f compose.run.yaml up --build
```

Застосунок: http://localhost:8080. Міграції та наповнення даними виконуються автоматично при першому запуску (повторний `up` дані не дублює). Увійдіть як `admin@example.com` / `password` (інші акаунти: [Тестові акаунти](#тестові-акаунти)).

Зупинити: `docker compose -f compose.run.yaml down`; з очищенням бази (свіжі дані при наступному запуску): `docker compose -f compose.run.yaml down -v`.

Це prod-подібний режим (`APP_ENV=production`, `APP_DEBUG=false`, FrankenPHP, без Node у фінальному образі). `APP_KEY` у `compose.run.yaml` демонстраційний і непридатний для реального продакшну.

## Розробка: запуск через Sail

Це шлях для розробки (гаряче перезавантаження, тести). Для швидкої перевірки без PHP і Node див. [Швидкий запуск](#швидкий-запуск-лише-docker).

Спершу потрібен `vendor/`, бо `vendor/bin/sail` з'являється лише після `composer install`: виконайте його на хості або, якщо PHP немає, в контейнері:

```bash
docker run --rm -u "$(id -u):$(id -g)" -v "$(pwd):/var/www/html" -w /var/www/html laravelsail/php84-composer:latest composer install --ignore-platform-reqs
```

Далі чотири команди:

```bash
cp .env.example .env
vendor/bin/sail up -d
vendor/bin/sail composer setup
vendor/bin/sail artisan db:seed
```

`composer setup` у контейнері ставить залежності, генерує `APP_KEY`, виконує міграції та збирає фронтенд. Застосунок: http://localhost, вхід `admin@example.com` / `password`. Для розробки з гарячим перезавантаженням фронтенду запустіть `vendor/bin/sail composer run dev`.

Префікс `vendor/bin/sail` потрібен, бо PHP, Composer і Node працюють усередині контейнера, а не на хості, і скрипт `sail` лежить у `vendor/bin/`. Щоб не набирати його щоразу: `alias sail='sh $([ -f sail ] && echo sail || echo vendor/bin/sail)'` (у `~/.zshrc` або `~/.bashrc`), тоді `sail up -d`, `sail artisan test` тощо.

Скинути базу й наповнити її заново:

```bash
vendor/bin/sail artisan migrate:fresh --seed
```

### Тести

```bash
vendor/bin/sail artisan test
```

Тести працюють на справжньому PostgreSQL, у базі `testing` (Sail створює її автоматично при першому створенні тому з базою). Повна перевірка (стиль, статичний аналіз і тести): `vendor/bin/sail composer test`.

## Запуск без Docker

Потрібні локально PHP 8.4+ з розширенням `pdo_pgsql`, Composer, Node.js 22 і PostgreSQL 18.

1. Створіть дві бази: `laravel` (робоча) і `testing` (для тестів); користувач БД має мати право створювати розширення (міграція виконує `CREATE EXTENSION pg_trgm`).
2. `cp .env.example .env` і в `.env` змініть `DB_HOST=127.0.0.1` та `DB_USERNAME` / `DB_PASSWORD` на свої.
3. Виконайте:

```bash
composer setup
php artisan db:seed
composer run dev
php artisan test
```

## Тестові акаунти

Створює seeder. Пароль у всіх: `password`.

| Роль | Email |
|---|---|
| Адміністратор | `admin@example.com` |
| Користувач 1 | `user1@example.com` |
| Користувач 2 | `user2@example.com` |

Seeder створює по 20 заявок у кожного користувача (10 «Нова», 6 «У роботі», 4 «Завершена») з історією змін статусу, разом 40 заявок. Реєстрації в застосунку немає.

## Рішення та припущення

- **Адміністратор не створює й не редагує заявки.** Це припущення: у завданні створення описане як дія користувача, а редагування тексту адміністратором не вимагається. Прямий запит адміністратора на створення отримує 403.
- **Чужа заявка: 404, а не 403.** Так не видно, чи існує заявка з таким ID (ID послідовні). 403 лише там, де заявку видно, але дія заборонена (наприклад, редагування власної заявки не в статусі «Нова»).
- **Явний цільовий статус.** Адміністратор надсилає статус, у який переводить заявку, а не «наступний крок». Дозволені переходи задає enum статусу, сервер відхиляє решту з помилкою валідації.
- **Блокування рядка.** Зміна статусу виконується в транзакції з блокуванням рядка заявки (`lockForUpdate`), тому два адміністратори не можуть зробити суперечливі переходи одночасно. Запис в історію й зміна статусу атомарні.
- **Права перевіряє сервер**, а не лише приховані кнопки: Policy на кожну дію, список будується від одного query scope «видимі для користувача».
- Статус і автор із запиту ігноруються: нова заявка завжди «Нова» й від поточного користувача, пріоритет за замовчуванням «Звичайний».
- Пошук за назвою: `ILIKE` із GIN-індексом `pg_trgm`. На малому обсязі даних планувальник обирає повний перегляд таблиці, і це очікувано.
- Історія містить лише переходи статусів; створення заявки не є зміною статусу.

## Відомі обмеження

- Сторінки автентифікації та налаштувань профілю (starter kit) лишилися англійською: повна локалізація потребує `laravel-vue-i18n` та перекладу рядків, яких немає в `laravel-lang`. Сторінки заявок, валідація й повідомлення українською.
- Немає реєстрації та верифікації email: акаунти створює seeder.
- Немає видалення заявок.
- Немає автотесту реальної гонки двох адміністраторів (потрібні два паралельні з'єднання з БД); захист забезпечує блокування рядка.

## Ідеї для покращення

- Повна i18n (включно зі сторінками auth і settings).
